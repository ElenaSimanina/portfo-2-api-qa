# Отчёт о тестировании API — Portfo 2

## 1. Общая информация

**Объект тестирования:** REST API проекта Portfo 2
**Инструмент:** Postman
**Коллекция:** `Portfo 2 — QA_Practical`

**Область тестирования:**
- авторизация пользователя;
- регистрация пользователя;
- получение `invite_hash` текущего пользователя;
- получение профиля зарегистрированного пользователя;
- обновление access-токена с помощью refresh-токена;
- исследовательские проверки обработки входных данных.

## 2. Результаты прогона

По результатам последнего зафиксированного прогона Postman:

| Показатель | Результат |
|---|---:|
| Всего assertions | 160 |
| Успешные assertions | 158 |
| Неуспешные assertions | 2 |
| Доля успешных assertions | 98,75% |

Доля успешных assertions рассчитана как отношение количества успешных проверок к общему количеству проверок.

**Важно:** количество assertions не равно количеству запросов или тест-кейсов. Результаты характеризуют выполнение автоматизированных проверок в конкретном прогоне коллекции.

## 3. Выявленный дефект

**BUG-001 — API регистрации принимает числовое значение `invite_hash`.**

При отправке запроса на регистрацию с числовым значением `invite_hash` API возвращает `201 Created`, и регистрация завершается успешно, хотя согласно контракту Swagger поле должно иметь тип `string`.

Дополнительные проверки показали:
- `null` — ответ `400 Bad Request`;
- boolean — ответ `400 Bad Request`;
- массив — ответ `400 Bad Request`;
- объект — ответ `400 Bad Request`;
- пустая строка — ответ `201 Created`.

Таким образом, поведение API различается в зависимости от переданного значения. Для числового значения выявлено несоответствие контракту API.

После регистрации пользователя с числовым `invite_hash` дополнительно проверено:
- созданный профиль доступен через API — `200 OK`;
- пользователь успешно проходит авторизацию — `200 OK`;
- при авторизации получены access- и refresh-токены.

Таким образом, передача значения неверного типа не препятствует созданию учётной записи и её последующему использованию.

Дефект задокументирован отдельно: BUG-001. Изменения с описанием дефекта внесены в репозиторий и объединены через Pull Request #1.

## 4. Исследовательские проверки

В рамках исследования дополнительно проверялась обработка некорректных форматов email при авторизации, а также регистрация с пустым `invite_hash`.

Для email без символа `@`, без доменной зоны и с пробелом API возвращал `401 Unauthorized`. Поскольку ожидаемое поведение для этих сценариев не было однозначно определено в Swagger, результаты зафиксированы как наблюдения, а не как подтверждённые дефекты.

Для регистрации с пустым `invite_hash` API вернул `201 Created`. Ожидаемое поведение для этого значения требованиями не определено, поэтому результат сам по себе не подтверждает наличие дефекта.

## 5. Ограничения тестирования

- Эндпоинт авторизации через Telegram Mini App (`POST /api/v1/authenticate/tg_miniapp/`) не тестировался: отсутствовал доступ к запуску приложения и необходимый сценарий входа.
- Не проверено, устанавливается ли связь между приглашённым и пригласившим пользователями при передаче числового `invite_hash`, а также начисляется ли пригласившему пользователю предусмотренный бонус. В доступной версии API не удалось проверить эти бизнес-процессы.
- Результаты относятся к проверенным сценариям и конкретному прогону коллекции; они не подтверждают полное покрытие API.
- Для некоторых проверок ожидаемое поведение не определено в Swagger, поэтому выводы ограничены фактически наблюдаемыми ответами API.
